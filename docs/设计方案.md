# 量化交易平台 设计方案

> 版本：v0.1（初稿）
> 状态：待评审
> 定位：一个**简易、可迭代**的内部量化数据与策略管理平台，先把分散的脚本统一管理起来，再逐步扩展。

---

## 1. 背景与目标

当前项目有两大类互相独立的 Python 脚本，只能逐个 `python xxx.py` 手动运行：

| 类别 | 位置 | 职责 | 代表脚本 |
|---|---|---|---|
| 数据类 | `script/` | 抓取/增量更新 A 股行情数据，产出 CSV/XLSX | 获取全量数据-日分组、获取增量数据-合并、获取全量增量复权因子 |
| 策略类 | `strategy/strategy/` | 读取数据做统计/回测，输出结果 Excel | A.py、A2.py、C.py、筛选低位股3.py |

**痛点**：
- 参数写死在脚本顶部（`START_DATE`、`DATA_DIR`、`OUT_FILE`、`MA_PERIODS` 等）；
- 输入输出目录写死，数据与结果的覆盖度/最新日期不透明；
- 无法统一触发、调度、追踪运行状态与结果。

**目标**：建设一个 Web 平台，统一管理「数据」和「策略/回测」，支持定时调度，并提供结果可视化。先做简易版本，逐步迭代。

---

## 2. 需求范围（四大核心能力）

| 能力 | 说明 |
|---|---|
| 数据管理 | 全量初始化、增量更新、复权因子合并的触发与状态；数据目录、最新日期、覆盖度、滞后天数查看 |
| 策略与回测管理 | 运行策略/回测、配置参数、查看运行记录与输出文件 |
| 定时调度 | 定时自动执行（如每日收盘后增量更新、定时回测） |
| 结果可视化 | 回测/统计结果的图表展示（净值、指标、覆盖情况等） |

**非目标（本期不做）**：真实模拟撮合、实盘下单、多用户权限、证券市场数据实时推送。

---

## 3. 总体架构

采用「保留脚本 + 平台调度」的经典分层设计，**不动原有脚本逻辑**，平台通过**适配器(Adapter)** 包装并调用它们。

```text
┌─────────────────────────────────────────────────────┐
│            多端消费者（共用同一套前端 UI）              │
│   Web 浏览器（本地访问）   Windows 桌面客户端           │
│                        (WebView2/Tauri 封装同一前端)    │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP/JSON（纯 REST API，无状态）
┌──────────────────────▼──────────────────────────────┐
│                  FastAPI 后端（REST 服务）             │
│  ├─ 数据 API   ├─ 策略/回测 API  ├─ 任务/调度 API      │
│  ├─ 元数据服务 ────────── SQLite（SQLAlchemy）         │
│  └─ 调度器（APScheduler，进程内）                      │
└──────────────────────┬──────────────────────────────┘
                       │ 调用（subprocess / import）
┌──────────────────────▼──────────────────────────────┐
│              适配器层 Adapters（薄壳，不改原逻辑）      │
│  script_adapter ─→ script/*.py                      │
│  strategy_adapter ─→ strategy/strategy/*.py          │
└──────────────────────┬──────────────────────────────┘
                       │ 读/写
┌──────────────────────▼──────────────────────────────┐
│         数据文件（保持现状） + 结果输出目录             │
└──────────────────────────────────────────────────────┘
```

设计要点：
- **一次性**把脚本的参数（顶部常量）和输入输出路径提取成**可配置项**，通过子进程传参或环境变量注入，脚本主体逻辑保持不变。
- **元数据库**只记录「元数据」（任务定义、运行记录、状态、文件位置、数据覆盖度），**主数据仍是原有文件**，避免重复造数据层。
- **调度在进程内**用 APScheduler，避免引入 Celery/Redis 等重组件，符合“简易迭代”。

### 3.1 多端访问架构（Web + Windows 桌面客户端）

**长远目标要求同时支持 Web 与 Windows 客户端访问，这决定了必须「前后端彻底分离」。**

> **部署目标：本地单机模式**。后端与全部数据/脚本跑在本机，Web 与桌面客户端都访问本机的同一个后端进程；本期不做远程部署与多用户，无登录鉴权需求。

- **后端 = 纯 REST API（无状态）**：不渲染页面、不托管前端路由、不依赖浏览器会话；只暴露 JSON 接口调用 `app/` 的业务逻辑。Web 和桌面客户端仅仅是同一套后端的两个消费者，共享全部数据、调度与任务状态。
- **前端只做一遍，两处复用**：Web 页与 Windows 客户端运行**同一套前端代码**，界面与交互完全一致，避免维护两套 UI。
  - Web：浏览器直接访问后端提供的静态站点（或独立 SPA）。
  - Windows 客户端：用 **WebView2（推荐，Win 自带运行时）** 或 **Tauri** 把同一套前端装扮成桌面窗口，仅负责外壳与本地集成（自动拉起/关闭后端进程、托盘、窗口管理等）。
- **开发顺序**：先做出「纯 API 后端 + Web 前端」形成闭环，桌面端只是对现有前端加一层外壳，成本低、不改变内核。
- **边界约束**：桌面端所有数据交互仍走后端 HTTP API，不直接读写数据库/脚本，保证两端行为与权限一致。

> **鉴权与 CORS（本地单机）**：本期不做登录/多用户，无需 token 鉴权。CORS 仅放行本机来源（`http://127.0.0.1` / `localhost` 及 WebView2 的本机资源），避免开放式跨域。若未来升级远程/多用户，因后端已是无状态 API，可在前端层统一加 token、CORS 再相应放开，两端共用，无需各自实现。

## 4. 技术栈选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.10+ | 与现有脚本生态一致（baostock/akshare/pandas/numpy）|
| 后端形态 | **纯 REST API（无状态，不渲染模板/不托管前端）** | 供 Web 与桌面客户端共用，一套后端多端访问 |
| Web 框架 | **FastAPI** + Uvicorn | 轻量、异步、自动生成 API 文档(/docs)，适合快速迭代 |
| 元数据库 | **SQLite**（SQLAlchemy ORM）| 单文件零运维，单机场景完全够用；后续可平滑换 PostgreSQL |
| 调度 | **APScheduler** | 进程内 cron 调度，定时增量更新/回测足够，无外部依赖 |
| 前端（Web） | **单页前端 + ECharts**（原生 JS 起步，随复杂度引入 Vue3）| 可视化与交互；无构建链、快速迭代 |
| 前端（Windows 客户端） | **WebView2（推荐）或 Tauri** 封装同一套 Web 前端成桌面应用 | UI 只做一遍，Web/桌面界面一致，成本最低 |
| 脚本调用 | subprocess（隔离）+ JSON 配置注入 | 保留脚本原样，降低回归风险 |
| 数据输出 | 沿用 Excel(openpyxl)/CSV；平台另行生成可视化所需摘要 | 兼容现有消费习惯 |

> 说明：前端建议**先用原生 JS + ECharts** 起步（无构建链、即改即所得），复杂度上来后再切 Vue3；桌面端不做第二套 UI，用 WebView2/Tauri 封装同一前端。**评审时确认取舍。**

## 5. 模块设计

### 5.1 数据管理模块（平台内建摄取，落 Parquet）

由于**不允许改动 `script/` 脚本**（其输出为 CSV 且不允许改造），平台主数据由**内建的数据摄取模块**直接从数据源抓取，并按 6.1 存储方案落为 **Parquet（按股票分文件）**，不再依赖现有脚本产出。

- **提供单一「获取数据」功能**（全量/增量/复权合并为一个动作）：
  - **单个「获取数据」按钮 + 可选「起始日期」输入**（留空=默认）。默认从 **2005-01-01** 开始（首库为全量回填；已建库则天然退化为增量续传）。便于测试时填一个较近的日期以缩小抓取窗口。
  - 抓取逻辑：从起始日期到当天，**逐交易日横扫全市场**，每日同时取不复权日K（`query_daily_history_k_AStock(date)`）与当日复权因子（`query_daily_adjust_factor(date)`），按 code join 后计算前/后复权价，**按股票写入** `data/market/daily_price/{code}.parquet`——该股无文件则新建（`write_stock`），有则追加（`merge_stock`，按日期去重）。
  - **已存在的日期不重复抓/不重复写**：以元数据库 `stock_freshness` 记录的**每股最新日期**为断点，凡「日期 ≤ 该股 latest_date」的，该股当日直接跳过；若某一日所有已知股票都已包含，则整日跳过（不请求数据源）。
  - 完成后在元数据库登记每只股票的最新日期（断点续传基线），更新最新日期、滞后天数、覆盖度。
- **复权实现（决策 2026-09-26）**：baostock 日线接口（`query_daily_history_k_AStock`）只能取得**不复权**行情；前/后复权需通过 `query_daily_adjust_factor` 取复权因子再换算。因此每行同时存储：原始价 + 前/后复权因子 + 前/后复权价，**一行取数即得全部复权档**，无需二次拉数或换算（字段布局见 6.1，共 24 列）。
- 数据源：**沿用 baostock（与现有 `script/` 口径一致）**，可选接入 akshare；通过「数据源适配器」隔离，方便替换。
- 断点续传：以元数据库「每股最新日期」（表 `stock_freshness`，见 6.3）为准，抓取中断后从上次日期继续。
- 运行过程落库为一次「任务」，实时更新状态（排队/运行中/成功/失败/部分失败/已终止）与日志进度。

### 5.2 策略与回测管理模块
- 每个策略登记为一条「策略定义」，含：可调参数 schema、数据依赖、输出文件路径。
- 运行= 按「策略定义 + 本次参数覆盖」触发一次子进程任务，记录运行状态与结果摘要（如超额、反转率、净值指标准入预留字段）。
- 历史运行记录可回溯，可重新运行。

### 5.3 调度模块
- 基于 APScheduler 的「定时任务」表：任务引用「数据/策略任务 + cron 表达式 + 参数覆盖」。
- 支持：启用/暂停、立即触发、查看下次运行时间与最近一次结果。
- 典型场景：`每日 17:00 增量更新数据`、`每周日 回测重算`。

### 5.4 结果可视化模块
- 前端 ECharts 图表：
  - 数据覆盖日历热力图 / 数据滞后天数时间线；
  - 策略结果对比（超额均值、胜率占比等）；
  - 回测净值/回撤曲线（预留，策略输出含序列数据时启用）。
- 后端提供「结果摘要」API，转成图表友好的 JSON，不要求在平台内重算。

## 6. 数据设计

### 6.1 主数据存储引擎选型（核心决策）

股票日K数据规模（A股全市场 10 年 ≈ 1200~1500 万行，每日约 5000 只 ≈ 5000 行/天）。负载特征：**写少读多、低频批量写入、高频“按股票 + 日期范围”读取**，属于典型的“按实体分片 + 列式优先”。

**推荐：Parquet 按股票分文件 + SQLite 元数据库 + DuckDB 分析读取。**

| 维度 | 方案 A（✅推荐）Parquet 按股票分文件 | 方案 B DuckDB 单文件 | 方案 C SQLite 单表 | 方案 D PostgreSQL/TimescaleDB | 方案 E ClickHouse |
|---|---|---|---|---|---|
| 存储形态 | 每股票一个 .parquet（列式） | 单个 .duckdb | 单 .db | 服务型数据库 | 列式分析库 |
| 新增（每日增量） | 抓当日 → 逐股 Merge 重写该股文件（每文件千行级，毫秒级） | APPEND 分区表 | INSERT + 复合索引 | 批量 INSERT + 复合索引 | 批量 INSERT，极快 |
| 查找（按股+区间） | 谓词下推 + 列裁剪，极快；`read_parquet` 直读 | SQL 查询，分析友好 | 单机，需合理索引 | 好，需运维 | 极快，适合跨股聚合 |
| pandas 契合 | 原生 | 好 | 需转换 | 好 | 驱动转换 |
| 运维成本 | 零（纯文件） | 零（单文件） | 极低 | 中（需跑服务） | 高 |
| 适用阶段 | 当前（简易迭代） | 可作为分析引擎 | 仅存元数据 | 后期规模化 | 后期大数据量聚合 |

**理由**：Parquet 列式存储契合“按股票取 K 线”，且把现状“按股 CSV”升级为 Parquet 仅是文件格式替换，数据语义不变、改动最小。元数据库(SQLite)记录“每股票最新日期、文件清单、数据状态”，支撑增量**断点续传**、覆盖度与滞后天数统计。跨股/全市场聚合用 DuckDB 直接读 Parquet，兼具 SQL 能力与零运维。

**演进路径**：当前用方案 A+B 即够；查询并发或数据量上规模后整体迁 ClickHouse 或 TimescaleDB，Parquet 便于离线导出与审计。

#### 跨股聚合的落地方式（DuckDB 不另存一份）

**数据全量只有 Parquet 一份。** DuckDB 是“查询引擎”，不是“第二份存储”。它通过 `read_parquet()` **惰性读取** Parquet 文件（列裁剪 + 谓词下推），只读需要的列与 row group，扫描完即弃，不向磁盘复制数据。无须建表、无须 `CREATE TABLE`，直接在内存连接上查询即可。

按股票分文件（`data/market/daily_price/{code}.parquet`），**每行共 24 列**：

```text
date, code,
open, high, low, close, preclose, volume, amount,   # 原始(不复权)价
turn, pctChg, tradestatus, isST,                     # 行情衍生
peTTM, pbMRQ, psTTM, pcfNcfTTM,                      # 估值(日线接口)
qfq_factor, hfq_factor,                              # 复权因子(adjust_factor 接口)
qfq_open, qfq_high, qfq_low, qfq_close,              # 前复权价
hfq_open, hfq_high, hfq_low, hfq_close               # 后复权价
```

（volume/amount 与复权无关，三个复权档共用一份；价格列仅扩展 open/high/low/close。）跨股聚合示例：

```sql
-- ① 全市场某日平均 PE（跨股聚合）
SELECT date, AVG(peTTM) AS mean_pe, COUNT(DISTINCT code) AS n
FROM read_parquet('data/market/daily_price/*.parquet')
WHERE date = '2025-01-02'
GROUP BY date;

-- ② 全市场某区间每只股票的年化波动率
SELECT code,
       STDDEV_SAMP(log(close / lag(close) OVER (PARTITION BY code ORDER BY date))) AS daily_vol
FROM read_parquet('data/market/daily_price/*.parquet')
WHERE date BETWEEN '2024-01-01' AND '2024-12-31'
GROUP BY code ORDER BY daily_vol DESC;
```

```python
import duckdb
con = duckdb.connect()                       # 内存连接即可，无需 db 文件
df = con.execute(
    "SELECT code, AVG(close) AS c FROM read_parquet('data/market/daily_price/*.parquet') "
    "WHERE date >= '2024-01-01' GROUP BY code"
).df()                                       # 转回 pandas，直接喂给回测
```

可作为“正式表”重复使用（仍是引用，不复制数据）：

```sql
CREATE VIEW all_k AS SELECT * FROM read_parquet('data/market/daily_price/*.parquet');
-- 之后直接 SELECT ... FROM all_k WHERE ...
```

**何时才“真入库”**：仅当高频反复做同一种全表聚合、且 Parquet 扫描明显偏慢时才物化 `CREATE OR REPLACE TABLE t AS SELECT * FROM read_parquet('data/market/daily_price/*.parquet')`。这会真正在 `.duckdb` 文件复制一份，**默认不需要**。

**性能注意**：按股票分文件时，跨股聚合（按日期维度横扫全市场）会扫到所有股票文件，靠列裁剪只读 `date/code/指标列` 控制开销；若“按日期横扫”成为高频动作，再考虑改为按年/月分区 + code 作列的布局以进一步裁剪。

> 说明：「平台日K数据」所在目录由 `config/config.yaml` 的顶层键 `data_dir` 配置（支持相对仓库根目录或绝对路径，默认 `data/market/daily_price`；相对路径不允许逃逸出仓库根），内建摄取写库、覆盖度扫描、数据集声明（`datasets[].dir`）均对齐该位置。

## 7. 现有脚本集成方案（关键）

> **定位调整（仅参考，不运行）**：`script/` 下的脚本**只作参考使用，不参与真正运行**，平台不调度它们，也不作为主数据来源。平台主数据由内建摄取模块抓取并落 Parquet（见 5.1）。`strategy/strategy/` 的策略/回测脚本仍作为**可运行的遗留脚本**，通过下列 manifest 机制接入、用 subprocess 调度。

### 7.1 脚本的存储与登记机制（manifest 扫描）

平台把「脚本本体（代码）」与「脚本登记（元数据）」分开管理。

**脚本本体——纯文件，放约定目录，纳入 git**
- 新增的数据/策略/回测脚本就是普通 `.py` 文件，放进对应约定目录即被平台识别，平台不搬走、不改写其内容：
  - `script/` 数据类脚本（获取全量/增量/复权）
  - `strategy/strategy/` 策略/回测脚本（沿用现状）
  - `strategy/backtest/` 回测脚本独立分目录（可选）
- 脚本本体由 git 版本管理，平台不干扰文件内容。

**登记元数据——声明式清单（manifest），与脚本同目录同名**
仅放 `.py` 无法让平台获知可配参数、数据依赖与输出，故每个脚本配一份 `.manifest.yaml`：

```yaml
# script/获取增量数据-合并.py.manifest.yaml
name: 每日增量更新
kind: script              # script=数据脚本 | strategy=策略 | backtest=回测
script: script/获取增量数据-合并.py
params:                    # 参数外置：覆盖脚本顶部常量
  start_date: {default: "2025-01-01", type: date, desc: 起始日期}
  end_date:   {default: "",           type: date, desc: 空=今天}
outputs:
  - dataset: 合并
    pattern: 合并/{code}.csv
```

```yaml
# strategy/strategy/A.py.manifest.yaml
name: MA60触线反转回测
kind: backtest
script: strategy/strategy/A.py
params:
  years:      {default: 10,          type: int,   desc: 回测年数}
  buffer:     {default: 0.01,        type: float, desc: 触线缓冲带}
  ma_periods: {default: [5,20,60,180], type: list[int], desc: 均线周期}
data_dep: A股日K数据
output: outputs/A_结果.xlsx
```

**新增脚本流程**：写 `.py` + 写同名 `.manifest.yaml` → 放入对应目录 → 平台「扫描目录」自动登记到元数据库 → UI 中改参数、点运行。

- manifest 仅做登记，参数覆盖的落地分两类：① 脚本已支持从命令行/环境变量取值时直接注入；② 不支持的，用 subprocess 以工作目录 + 临时参数化副本运行，**优先不动原文件**。
- 清单文件跟随代码进 git，便于迁移与协作。
- 对照方案：不用 manifest 文件、改为数据库手工登记或解析脚本头部约定注释。**推荐 manifest 文件方式**：声明式、直观、可版本管理。

### 7.2 参数外置与运行

- **不修改原脚本逻辑**，仅做“参数外置”：
  1. 阅读脚本顶部常量，识别可配置参数；
  2. 用 `config/` 下的 JSON（或命令行参数/环境变量）覆盖这些常量；
  3. 通过 **subprocess** 运行脚本，实时抓取 stdout/stderr 写日志。
- 对无法参数化的硬编码路径（如 `DATA_DIR = "A股日K数据"`），优先用「运行时工作目录 + 只读映射」或用环境变量配 `config.ini`，避免改动代码。
- 遇到必须改脚本才能暴露参数的，**先记录到「适配清单」，评审后小步修改**，并保留原脚本备份。

### 7.3 脚本间数据契约

同一批策略脚本（A2.py、C.py 等）常共用同一份 `A股日K数据`。在 manifest 中以 `data_dep` + `outputs` 表达依赖关系：某策略声明读入 `dataset: A股日K数据`，平台据此判断「运行该回测前是否需要先刷新对应数据」，并在数据管理页展示其依赖。跨脚本的中间产物同样以 `outputs/dataset` 声明，便于回测直接引用。

## 9. 前端页面设计（初版）

> 本套页面即为**唯一前端**，Web 浏览器与 Windows 桌面客户端共用；桌面端仅做外壳封装，页面、交互、图表完全一致。

1. **数据管理页**：单个「平台日K数据」卡片（股票数、最新数据日期、滞后天数、覆盖度基于 Parquet 实际扫描），含**起始日期输入框**（留空=默认断点续传/2005-01-01）与单个**「获取数据」按钮**；`script/` 遗留 CSV 目录不再作为平台数据集展示。
2. **策略/回测页**：策略列表、参数表单、运行按钮、历史运行记录；点击查看结果图与日志。
3. **调度页**：定时任务列表、cron 展示、启用/暂停、立即运行、下次运行时间。

## 11. 风险与注意事项

- **脚本为黑盒**：若脚本内部阻塞或长时间挂起，需设定任务超时（超时自动 kill）**与手动终止**：任务页「终止」按钮调用 `POST /api/tasks/{id}/terminate`，终止运行中的子进程并将任务状态标记为「已终止」。
- **并发**：同一策略/数据任务默认串行，防止子进程互相踩数据目录；后续可加资源锁。
- **日志中文编码**：Windows 下需统一 UTF-8 处理 stdout，避免乱码。
- **磁盘与内存**：全量合并脚本内存占用高（~3GB），调度时应避开高峰并存量提醒。
